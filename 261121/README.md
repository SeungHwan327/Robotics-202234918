## 1. 수업 개요와 학습 목표

로봇은 주변 환경을 측정하는 센서, 데이터를 처리하는 제어기, 실제 움직임을 만드는 구동기로 구성된다. 이 수업에서는 ESP32 기반 보드에서 센서와 모터를 다루는 방법을 익히고, ROS 2에서 서로 다른 프로그램이 메시지를 주고받는 구조를 학습한다.

임베디드 실습의 핵심은 센서에서 전달되는 바이트를 물리량으로 해석하는 과정이다. ROS 2 실습의 핵심은 기능을 노드로 나누고, 공통된 메시지 형식과 토픽을 통해 연결하는 과정이다. 두 영역을 함께 이해하면 센서 측정부터 로봇 제어 명령까지 이어지는 전체 구조를 설계할 수 있다.

학습 목표는 다음과 같다.

- ESP32의 GPIO를 사용해 네 개 모터의 회전 방향을 개별적으로 확인한다.
- UART와 I²C의 차이를 설명하고 센서 통신 설정에 적용한다.
- LiDAR의 47바이트 패킷을 해석하여 각도별 거리 데이터를 구성한다.
- MPU6050의 가속도·각속도 원시 데이터를 읽어 실제 단위로 변환한다.
- ROS 2의 Node, Topic, Message, Publisher, Subscriber를 이해한다.
- DDS, Domain ID, QoS가 통신에 미치는 영향을 설명한다.
- Python 패키지를 빌드하고 talker와 listener의 통신을 확인한다.

## 4. MCU와 임베디드 프로그램의 기본 구조

### 4.1 MCU의 역할

MCU(Microcontroller Unit)는 CPU, 메모리, GPIO, 타이머, 통신 주변장치 등을 포함하는 제어용 장치이다. 본 실습의 ESP32는 GPIO로 모터 드라이버를 제어하고 UART와 I²C로 센서 값을 수신한다.

모터는 ESP32 핀에서 직접 구동하지 않는다. MCU는 제어 신호를 만들고, 모터 드라이버가 모터에 필요한 전류와 전압을 공급하는 역할을 맡는다.

### 4.2 `setup()`과 `loop()`

- `setup()`은 시작 시 한 번 실행되며 핀 모드와 통신을 초기화한다.
- `loop()`는 이후 반복 실행되며 센서 수신과 제어 동작을 수행한다.
- `delay()`는 간단한 동작 순서를 만들기 쉽지만, 같은 실행 흐름의 다음 작업을 지연시킨다.

모터 개별 시험에서는 일정 시간 회전시키는 방식이 이해하기 쉽다. 반면 실시간 센서 처리에서는 긴 지연이나 무한 대기가 센서 처리와 정지 판단을 늦출 수 있으므로 비차단 구조를 검토해야 한다.

## 5. 직렬 통신 이론: UART와 I²C

### 5.1 동기식과 비동기식

동기식 통신은 별도의 클록 신호를 기준으로 데이터를 교환한다. 비동기식 통신은 별도의 클록 선 없이 사전에 정한 전송 속도와 프레임 형식으로 비트의 시간을 해석한다.

비동기식이라고 장치 내부에 클록이 없는 것은 아니다. 각 장치는 내부 클록을 사용하고, 수신기는 시작 비트를 기준으로 샘플링 시점을 맞춘다. 버퍼와 타이밍 관리 역시 두 방식 모두에서 중요하다.

| 항목 | UART | I²C |
| --- | --- | --- |
| 동기 방식 | 비동기 | 동기 |
| 주요 신호 | TX, RX | SDA, SCL |
| 별도 클록 선 | 없음 | SCL 사용 |
| 설정·식별 | baud rate, 데이터·패리티·정지 비트 | 주소, 버스 속도, 레지스터 |
| 실습 대상 | LiDAR | MPU6050 |

### 5.2 UART

UART는 Universal Asynchronous Receiver/Transmitter의 약자이다. 한 장치의 TX는 다른 장치의 RX로 연결하며, 공통 GND를 통해 전압의 기준을 공유한다.

실습의 `SERIAL_8N1`은 데이터 8비트, 패리티 없음, 정지 비트 1개를 뜻한다. 일반적인 UART 프레임에는 시작 비트도 포함된다. 기본적인 UART 전송에서는 데이터가 보통 LSB부터 전송되지만, 여러 바이트로 이루어진 정수의 바이트 순서는 센서 패킷 규격에서 별도로 정한다.

UART와 USB는 서로 다른 규격이다. PC에서 USB를 통해 직렬 모니터를 여는 과정에 USB-UART 변환 장치가 사용될 수 있지만, 두 통신 방식을 동일하게 취급하지 않는다.

### 5.3 Baud rate와 데이터 처리량

LiDAR 코드는 센서 수신에 `230400`, 시리얼 모니터 출력에 `115200`을 사용한다. 두 포트의 역할이 다르므로 서로 다른 속도를 사용할 수 있다.

8N1에서 한 바이트 전송에는 시작·정지 비트를 포함해 일반적으로 10비트가 필요하다. 따라서 230400 baud는 이론적으로 초당 약 23040바이트에 해당한다. 실제 유효 측정량은 패킷 구조, 송신 주기, 버퍼 처리에 따라 달라진다.

### 5.4 I²C

I²C는 여러 주변장치를 SDA와 SCL 두 신호선으로 연결하는 동기식 직렬 버스이다. 본 실습에서는 ESP32가 통신을 시작하고 MPU6050의 주소와 레지스터를 지정한다.

- SDA: 데이터 전달
- SCL: 클록 전달
- 주소: 같은 버스에서 대상 장치를 구분
- ACK: 수신 측의 응답
- NACK: 응답하지 않거나 읽기 종료 등을 표시

일반적인 7비트 주소 방식에서는 주소 7비트와 R/W 1비트가 함께 전송된다. SDA와 SCL은 풀업을 사용하는 구조이며, 시작 조건은 SCL이 높은 동안 SDA가 HIGH에서 LOW로 변하는 것이다. 단순히 클록이 LOW가 되는 것이 시작 조건은 아니다.

## 6. 실습 1 — 네 개 모터의 방향 제어

### 6.1 핀 배치

| 모터 | 약어 | IN1 | IN2 |
| --- | --- | --- | --- |
| 앞 오른쪽 | FR, Front Right | GPIO 26 | GPIO 25 |
| 앞 왼쪽 | FL, Front Left | GPIO 19 | GPIO 27 |
| 뒤 오른쪽 | RR, Rear Right | GPIO 23 | GPIO 12 |
| 뒤 왼쪽 | RL, Rear Left | GPIO 0 | GPIO 15 |

`motorPins[8]` 배열은 각 모터의 두 제어 핀을 차례대로 저장한다. 반복문의 인덱스가 2씩 증가하므로 한 번에 모터 한 개의 핀 쌍을 선택한다.

### 6.2 초기화

`Serial.begin(115200)`으로 직렬 포트를 준비하고, 모든 모터 핀을 `OUTPUT`으로 설정한다. 초기 출력은 모두 LOW이다.

이 테스트는 PWM을 사용하지 않는다. 즉, 속도 조절보다 배선과 회전 방향을 확인하는 코드이다.

### 6.3 모터 한 개의 동작 순서

| 순서 | IN1 | IN2 | 유지 시간 | 코드의 의도 |
| --- | --- | --- | --- | --- |
| 1 | HIGH | LOW | 1000 ms | 한 방향 회전 |
| 2 | LOW | LOW | 200 ms | 정지 명령 |
| 3 | LOW | HIGH | 1000 ms | 반대 방향 회전 |
| 4 | LOW | LOW | 200 ms | 정지 명령 |

모터 한 개당 지연 시간 합계는 2.4초이다. 네 개를 순차 시험하므로 전체 지연 시간은 약 9.6초이며 함수 실행 시간은 별도로 더해진다.

HIGH/LOW 조합이 차체의 전진인지 후진인지는 모터 설치 방향과 배선에 따라 달라진다. 좌우 모터가 대칭으로 장착되면 같은 전기적 명령에서도 바퀴의 차체 기준 방향이 다를 수 있다. LOW/LOW의 제동·공회전 여부 또한 드라이버 사양에 따라 판단해야 한다.

### 6.4 실습 절차와 확인 항목

1. 바퀴가 자유롭게 돌 수 있는 상태에서 시험한다.
2. 실제 배선을 위 GPIO 표와 비교한다.
3. `motor_test.ino`를 업로드한다.
4. 앞 오른쪽부터 네 모터가 순차적으로 움직이는지 확인한다.
5. 각 모터가 두 방향으로 회전하고 중간에 정지하는지 기록한다.
6. 이후 주행 함수에서 사용할 차체 기준 전진·후진 방향을 정리한다.

ESP32의 GPIO 0, 12, 15 등은 보드에 따라 부팅 시 상태가 중요한 핀일 수 있다. 업로드나 부팅 문제가 발생하면 모터 드라이버 연결 상태와 보드 핀 사양을 함께 확인한다.

## 7. 실습 2 — LiDAR UART 패킷 해석

### 7.1 각도 기준

이 실습의 주석은 다음 차체 방향을 정의한다.

| 각도 | 차체 방향 |
| --- | --- |
| 0° | 뒤, Back |
| 90° | 왼쪽, Left |
| 180° | 앞, Front |
| 270° | 오른쪽, Right |

이 기준은 해당 센서 장착 상태에 대한 실습 기준이다. ROS 좌표계와 자동으로 동일한 것은 아니며, 실제 장애물을 각 방향에 놓아 확인해야 한다.

### 7.2 UART 설정

```cpp
#define LIDAR_RX 16
Serial.begin(115200);
Serial2.begin(230400, SERIAL_8N1, LIDAR_RX, -1);
```

LiDAR TX에서 보내는 데이터를 ESP32 GPIO 16으로 받는다. 마지막 인수 `-1`은 이 설정에서 TX 핀을 지정하지 않는다는 의미이다. 현재 코드는 명령 송신 없이 수신 데이터 해석에 집중한다.

### 7.3 47바이트 패킷 구조

| 바이트 인덱스 | 크기 | 내용 |
| --- | --- | --- |
| 0 | 1 | 헤더 `0x54` |
| 1 | 1 | VerLen `0x2C` |
| 2–3 | 2 | 회전 속도 |
| 4–5 | 2 | 시작 각도 |
| 6–41 | 36 | 측정점 12개: 거리 2바이트 + confidence 1바이트 |
| 42–43 | 2 | 끝 각도 |
| 44–45 | 2 | timestamp |
| 46 | 1 | CRC |

코드는 이 중 헤더, 시작·끝 각도, 거리 값을 사용한다. 회전 속도, confidence, timestamp, CRC는 패킷에 포함되어 있어도 현재 판단에 사용되지 않는다.

### 7.4 두 바이트를 정수로 결합

```cpp
uint16_t readUInt16(uint8_t low, uint8_t high) {
    return low | (high << 8);
}
```

하위 바이트가 먼저 오는 little-endian 데이터를 16비트 정수로 복원한다. 예를 들어 `low = 0x34`, `high = 0x12`이면 결과는 `0x1234`, 즉 4660이다.

비트 시프트 `<< 8`은 상위 바이트를 정수의 상위 8비트 위치로 이동시킨다. OR 연산은 하위 바이트와 상위 바이트를 하나로 합친다.

### 7.5 시작·끝 각도와 보간

각도 원시 값은 0.01도 단위이므로 100.0으로 나눈다.

```text
startAngle = startRaw / 100.0
endAngle   = endRaw / 100.0
angleStep  = (endAngle - startAngle) / 11.0
angle(i)   = startAngle + angleStep × i,  i = 0 ... 11
```

측정점은 12개지만 양 끝 사이의 구간은 11개이다. 따라서 각도 간격 계산에서 12가 아닌 11로 나눈다.

끝 각도가 시작 각도보다 작으면 360도를 더하여 경계를 통과한 패킷을 해석한다. 예를 들어 358도에서 2도까지의 범위는 계산 중 358도에서 362도로 취급하고, 개별 측정점 저장 전에 다시 0~360도 범위로 돌린다.

### 7.6 거리 배열 구성

`uint16_t distances[360]`은 정수 각도별 거리 슬롯이다. 각도를 반올림한 인덱스에 mm 단위 거리를 저장한다. 360으로 반올림되면 인덱스 0으로 바꾼다.

- 거리 0은 저장하지 않는다.
- 같은 각도 슬롯에 여러 측정점이 들어오면 나중 값이 덮어쓴다.
- 모든 1도 슬롯이 매 회전 반드시 측정되는 것은 아니다.
- 배열을 회전마다 초기화하지 않으므로 이전 회전 값이 남을 수 있다.

따라서 이 배열은 완전하게 동기화된 최신 360도 스캔이라고 단정할 수 없다. 실제 제어에 활용하려면 측정 시각과 유효성 정보가 필요하다.

### 7.7 한 바퀴 감지와 출력

이전 각도가 300도보다 크고 현재 각도가 60도보다 작으면 회전 경계를 통과했다고 보고 전체 배열을 출력한다. 코드는 해당 현재 측정점을 저장하기 **전에** 출력 함수를 호출한다.

예상 출력 형식:

```text
0 deg : 1250 mm
1 deg : 1248 mm
...
359 deg : 1260 mm
----------------
```

위 숫자는 형식 설명용 예시이며 실제 측정값이 아니다.

### 7.8 현재 코드의 한계와 개선 방향

1. **CRC 미검증:** 전송 오류가 있는 패킷도 거리 값으로 사용될 수 있다.
2. **수신 타임아웃 없음:** 패킷 중간에서 데이터가 끊기면 `while`에서 계속 기다릴 수 있다.
3. **confidence 미사용:** 신뢰도가 낮은 측정점을 구분하지 않는다.
4. **오래된 값 잔존:** 슬롯마다 갱신 시각을 저장하는 방식이 필요하다.
5. **출력 부하:** 회전마다 360줄을 출력하면 송신 버퍼 대기와 처리 지연이 발생할 수 있다.
6. **각도 단순 보간:** 센서 규격의 보정식이 필요하다면 추가해야 한다.

개선 시에는 패킷 상태 머신, 수신 시간 제한, CRC 검사, 유효 플래그, 제한된 출력 주기를 함께 고려한다.

## 8. 실습 3 — MPU6050 IMU 측정

### 8.1 IMU란?

IMU(Inertial Measurement Unit)는 관성 측정 장치이다. MPU6050은 3축 가속도계와 3축 자이로스코프를 제공한다. 이 코드에서는 지자기 센서 값을 읽지 않는다.

| 센서 | 측정량 | 실습 출력 단위 |
| --- | --- | --- |
| Accelerometer | 축 방향 가속도 측정값 | m/s² |
| Gyroscope | 축 주위 각속도 | deg/s |

각속도는 각도 자체가 아니다. 이를 시간에 대해 적분하면 회전각 변화를 추정할 수 있지만, 센서 바이어스가 누적되어 드리프트가 발생할 수 있다.

### 8.2 I²C 핀과 주소

```cpp
#define SDA_PIN 21
#define SCL_PIN 22
#define MPU_ADDR 0x68
```

주소는 코드에서 `0x68`로 가정한다. 실제 주소는 센서 보드의 주소 선택 상태에 따라 확인해야 한다.

### 8.3 센서 깨우기

`setup()`은 전원 관리 레지스터 `0x6B`를 선택한 뒤 `0x00`을 쓴다. 이는 슬립 상태를 해제하려는 초기화이다.

현재 코드는 통신 성공 여부를 초기화 단계에서 검사하지 않으며, 측정 범위 레지스터도 명시적으로 설정하지 않는다. 따라서 변환 계수는 센서가 기대하는 기본 범위에 있다는 전제로 해석해야 한다.

### 8.4 14바이트 연속 읽기

`0x3B`부터 다음 데이터를 읽는다.

| 순서 | 데이터 | 크기 |
| --- | --- | --- |
| 1 | 가속도 X, Y, Z | 6바이트 |
| 2 | 온도 | 2바이트 |
| 3 | 각속도 X, Y, Z | 6바이트 |

`Wire.endTransmission(false)`는 레지스터 주소 지정 후 STOP을 보내지 않고 이어지는 읽기를 준비한다. 온도 값은 출력에 사용하지 않지만, 바이트 위치를 맞추기 위해 반드시 읽어서 소비한다.

수신 바이트가 14개보다 적으면 `MPU6050 read failed`를 출력하고 이번 측정을 건너뛴다.

### 8.5 부호 있는 원시 값 복원

```cpp
int16_t ax_raw = (Wire.read() << 8) | Wire.read();
```

IMU 데이터는 상위 바이트를 먼저 읽는다. LiDAR 코드와 바이트 순서가 다르므로 같은 결합 함수를 그대로 적용하면 안 된다.

또한 가속도와 각속도는 음수가 가능하므로 `int16_t`를 사용한다. 비트 패턴을 부호 있는 값으로 해석해야 반대 방향 움직임도 표현할 수 있다.

### 8.6 단위 변환

코드의 변환식은 다음과 같다.

```text
acceleration [m/s²] = raw / 16384.0 × 9.80665
angular velocity [deg/s] = raw / 131.0
```

이 계수는 가속도계 ±2g, 자이로 ±250 deg/s 설정을 전제로 한다. 예를 들어 가속도 원시 값이 16384이면 약 9.80665 m/s², 자이로 원시 값이 131이면 약 1 deg/s이다.

센서 범위를 바꾸면 감도가 달라지므로 변환 계수도 바꾸어야 한다. 확장 시에는 초기화 코드에서 범위를 명시하고 레지스터 읽기로 확인하는 것이 좋다.

### 8.7 정지 상태에서도 가속도 값이 나타나는 이유

가속도계의 출력은 중력의 영향이 포함된 측정값이므로, 정지 상태라고 세 축이 모두 0이 되지는 않는다. 센서가 수평에 가까우면 한 축에 약 9.8 m/s² 크기가 나타날 수 있다.

강의 메모의 Z축 약 -9.8은 특정 장착 방향에서의 예이다. 부호는 센서 축 방향과 장착 자세에 따라 달라진다. 센서를 뒤집으면 해당 축의 부호가 바뀔 수 있다.

### 8.8 출력과 확인 방법

```text
Accel [m/s^2]: 0.120, -0.080, 9.790 | Gyro [deg/s]: 0.03, -0.05, 0.02
```

이 역시 형식 예시이다. 실제로는 다음을 확인한다.

1. 정지 상태에서 가속도 벡터 크기가 대략 1g에 가까운지 확인한다.
2. 센서를 기울여 중력 성분이 축 사이에서 변하는지 관찰한다.
3. 한 축 주위로 회전시키고 해당 각속도 값의 부호와 크기를 확인한다.
4. 정지 상태의 자이로 바이어스를 기록한다.

`delay(100)`이 있으므로 반복 주기는 약 100 ms 이상이다. 통신과 출력 시간이 더해지기 때문에 정확한 10 Hz라고 단정할 수 없다.

## 9. ROS 2 이론

### 9.1 ROS는 일반적인 운영체제인가?

ROS(Robot Operating System)는 로봇 소프트웨어 개발을 위한 프레임워크와 도구 생태계이다. Linux 같은 운영체제 커널을 대체하지 않는다. 운영체제 위에서 메시지 통신, 패키지 관리, 장치 드라이버, 시각화, 로봇 알고리즘을 연결한다.

- 하드웨어 추상화: 장치별 세부 구현을 공통 인터페이스로 감싼다.
- 통신: 센서, 제어, 판단 기능 사이에서 데이터를 전달한다.
- 재사용: 패키지 단위로 기능을 공유한다.
- 도구: RViz와 같은 시각화 및 디버깅 도구를 활용한다.

Gazebo는 로봇 시뮬레이터로, ROS와 연동해 사용할 수 있다. RViz는 주로 센서·좌표계·로봇 상태를 시각화하며 물리 시뮬레이터와 역할이 다르다.

### 9.2 ROS 1과 ROS 2

ROS 1은 노드 발견과 등록에 ROS Master를 사용한다. 데이터 자체가 항상 Master를 경유하는 것은 아니다. ROS 2의 일반적인 DDS 기반 구성에서는 별도 ROS Master 없이 분산 발견과 통신을 수행한다.

ROS 2는 QoS 설정과 보안 기능을 지원한다. 다만 ROS 2를 사용한다는 이유만으로 모든 통신이 자동으로 암호화되거나 인증되는 것은 아니며 보안 설정이 필요하다. 지원 운영체제와 설치 방식은 배포판별로 확인해야 한다.

### 9.3 Node

노드는 로봇 시스템에서 하나의 기능을 담당하는 논리적인 실행 단위이다. 센서 읽기, 경로 계획, 모터 명령 등을 별도 노드로 나눌 수 있다.

**노드 1개 = 프로세스 1개 = 터미널 1개 = 로봇 1대라는 등식은 성립하지 않는다.** 한 프로세스에 여러 노드가 있을 수 있고, 한 로봇은 보통 여러 노드를 사용한다. 터미널은 실행 도구일 뿐이다.

### 9.4 Topic과 Message

Topic은 메시지를 발행하고 구독하는 이름 있는 통신 채널이다. Message는 그 채널에서 전달되는 데이터의 형식과 실제 내용이다.

| 개념 | 실습 값 |
| --- | --- |
| 발행 노드 | `talker` |
| 구독 노드 | `listener` |
| 토픽 이름 | `/demo_topic` |
| 메시지 타입 | `std_msgs/msg/String` |
| 메시지 내용 | `Hello ROS2: <경과 초>` |

토픽 이름과 메시지 타입을 맞추어야 하며, Domain ID와 QoS 등 통신 조건도 호환되어야 한다. `/`는 계층적인 이름 구성을 나타낸다. 예를 들어 `/robot1/imu`와 `/robot2/imu`는 서로 다른 토픽 이름이다.

### 9.5 Topic, Service, Action

| 방식 | 특징 | 사용 예 |
| --- | --- | --- |
| Topic | 연속적인 발행·구독 | LiDAR 스캔, IMU 측정 |
| Service | 요청과 응답 | 설정 조회, 초기화 요청 |
| Action | 장시간 작업의 목표·피드백·결과, 취소 | 목표 지점 이동 |

센서 값처럼 계속 갱신되는 데이터는 Topic이 자연스럽다. 한 번의 요청에 결과가 필요한 작업은 Service, 진행 상황을 확인하며 오래 수행하는 작업은 Action으로 구분할 수 있다.

### 9.6 로봇 메시지와 물리량

| 메시지 계열 | 대표 예 | 의미 |
| --- | --- | --- |
| `std_msgs` | `String` | 기본 데이터 |
| `geometry_msgs` | `Pose`, `Twist`, `TwistStamped` | 위치·자세·속도 |
| `sensor_msgs` | `Imu`, `LaserScan` | 관성·거리 센서 |
| `nav_msgs` | `Odometry`, `OccupancyGrid` | 이동 추정·지도 |

Pose는 position과 orientation으로 구성된다. Orientation은 흔히 quaternion으로 표현된다. Twist는 선속도 `linear`와 각속도 `angular`를 포함한다. TwistStamped는 Twist에 시간과 좌표계 정보를 담는 Header를 더한 메시지이다.

실제 접근 문법은 언어에 따라 다르다. ROS Python에서는 보통 `msg.pose.position.x`, `msg.twist.linear.x`처럼 소문자 필드를 사용한다. 메시지 종류에 따라 중첩 경로도 달라진다.

`package.xml`에 여러 메시지 패키지가 선언되어 있어도 제공된 talker와 listener가 실제로 사용하는 메시지는 String이다.

## 10. DDS, Domain ID, QoS

### 10.1 DDS

DDS(Data Distribution Service)는 데이터 중심의 분산 통신 표준이다. 일반적인 ROS 2 구성에서 미들웨어 구현이 노드 발견과 메시지 전달을 지원한다. 사용자는 `rclpy`에서 publisher와 subscription을 만들고 미들웨어는 그 통신을 처리한다.

### 10.2 ROS_DOMAIN_ID

Domain ID는 통신 참여자를 도메인 단위로 구분한다. 같은 네트워크에서도 다른 ID를 사용하면 일반적으로 서로의 노드를 발견하지 않는다.

```bash
export ROS_DOMAIN_ID=23
```

23은 예시이다. 수업에서 지정한 값을 사용하고 관련 터미널에 동일하게 설정한다. 사용할 수 있는 범위와 다른 시스템과의 충돌은 환경에 따라 확인해야 한다. Domain ID는 보안 인증이나 접근 제어의 대체 수단이 아니다.

### 10.3 QoS: 전달 방식을 정하는 정책

QoS(Quality of Service)는 신뢰성, 이력, 지속성 등 메시지 전달 동작을 정한다.

| 정책 | 선택 | 의미 |
| --- | --- | --- |
| Reliability | Reliable | 손실 복구와 재전송을 지원 |
| Reliability | Best Effort | 전달을 보장하지 않고 가능한 범위에서 전송 |
| Durability | Volatile | 늦게 연결한 구독자에게 이전 샘플을 보존해 주지 않음 |
| Durability | Transient Local | 발행자 측에 보존한 샘플을 늦은 구독자에게 제공 가능 |
| History | Keep Last | 최근 N개 이력 유지 |
| Depth | 정수 N | Keep Last에서 유지할 샘플 수 |

Reliable은 지연이 전혀 없다는 뜻이 아니다. Best Effort도 모든 메시지를 반드시 더 빠르게 처리한다는 보장은 없다. 손실 복구 비용과 최신성 사이에서 데이터 성격에 맞는 정책을 선택한다.

지도와 같이 늦게 참여한 노드도 받아야 하는 데이터에는 Transient Local을 검토할 수 있다. 보존량은 history와 depth 등에 좌우되며 단순히 몇 초 동안만 저장한다는 뜻은 아니다.

### 10.4 QoS 호환성

토픽 이름과 타입이 같아도 발행자가 제공하는 QoS와 구독자가 요구하는 QoS가 호환되지 않으면 통신이 성립하지 않을 수 있다. 예를 들어 Best Effort 발행자에 Reliable 구독자가 연결되기를 요구하면 신뢰성 조건이 맞지 않는다.

실습 코드의 마지막 인수 `10`은 주기나 전송 횟수가 아니라 QoS 이력 깊이이다. 상세 정책을 명시적으로 구성하려면 `QoSProfile`을 사용한다.

## 11. Colcon workspace와 Python 패키지

### 11.1 워크스페이스 디렉터리

| 디렉터리 | 내용 | 관리 방식 |
| --- | --- | --- |
| `src/` | 개발자가 작성한 패키지 소스 | 주된 버전 관리 대상 |
| `build/` | 빌드 중간 결과 | 도구가 생성 |
| `install/` | 실행 파일과 설치 환경 | 도구가 생성 |
| `log/` | 빌드·테스트 로그 | 도구가 생성 |

`colcon build`는 일반적으로 워크스페이스 최상위에서 실행한다. Python 모듈이 들어 있는 가장 안쪽 폴더에서 실행하는 방식과 구분해야 한다.

### 11.2 제공 패키지 이름에 대한 점검

제공된 `package.xml`, `setup.py`, `setup.cfg`는 패키지 이름으로 `1_pubsub`을 사용한다. ROS 패키지 이름은 문자로 시작해야 하므로 이 이름은 수정이 필요한 항목이다. Python 실행 진입점 해석에서도 숫자로 시작하는 모듈 경로가 문제를 일으킬 수 있다.

아래 재현 절차는 **수정 예시 이름 `pubsub_demo`**를 사용한다. 업로드된 원본 파일을 이 문서에서 수정한 것은 아니다.

이름을 바꿀 때는 다음 항목을 일관되게 맞춘다.

1. ROS 패키지 최상위 폴더 이름
2. `package.xml`의 `<name>`
3. `setup.py`의 `package_name`
4. Python 모듈 폴더 이름
5. `resource/` 내부 마커 파일 이름
6. `setup.cfg`의 두 설치 경로
7. `setup.py`의 `console_scripts` 모듈 경로

Python 모듈 폴더의 `__init__.py`와 resource 마커도 필요하다. 이 두 파일은 제공 목록에서 확인되지 않았으므로 실제 패키지에 존재하는지 점검한다.

### 11.3 파일별 역할

`package.xml`은 패키지 이름과 의존성을 선언한다. 제공 파일에는 `rclpy`, `std_msgs`, `geometry_msgs`, `sensor_msgs`, `nav_msgs`가 있다. 설명과 라이선스는 TODO이므로 제출·공유 전에 실제 내용으로 정리한다.

`setup.py`는 setuptools를 통해 Python 코드를 설치한다. `find_packages()`는 Python 패키지를 탐색하고 `data_files`는 ROS 패키지 발견에 필요한 파일을 설치한다. `entry_points`는 `ros2 run`으로 실행할 이름과 Python 함수를 연결한다.

수정 예시:

```python
package_name = 'pubsub_demo'
# setup(...) 내부
entry_points={
    'console_scripts': [
        'talker = pubsub_demo.talker:main',
        'listener = pubsub_demo.listener:main',
    ],
},
```

`setup.cfg`도 다음처럼 맞춘다.

```ini
[develop]
script_dir=$base/lib/pubsub_demo
[install]
install_scripts=$base/lib/pubsub_demo
```

## 12. 실습 4 — ROS 2 Publisher와 Subscriber

### 12.1 Talker 코드 흐름

1. `rclpy.init()`으로 ROS 클라이언트 라이브러리를 초기화한다.
2. `Talker()`를 생성하고 노드 이름을 `talker`로 지정한다.
3. `/demo_topic`의 String publisher를 생성한다.
4. 노드 생성 시각을 `time.time()`으로 저장한다.
5. 1.0초 주기의 타이머를 등록한다.
6. 타이머 콜백에서 경과 시간을 정수로 계산한다.
7. String 메시지에 `Hello ROS2: <경과 시간>`을 넣고 발행한다.
8. 같은 내용을 로그에 출력한다.

메시지의 숫자는 단순한 메시지 개수 카운터가 아니다. 시작 이후 경과 시간을 정수로 바꾼 값이다. 시스템 시간 변경이나 콜백 지연이 있으면 1씩 정확히 증가하지 않을 수 있다.

`create_timer(1.0, ...)`도 엄격한 실시간 실행을 보장하지 않는다. 실행 환경의 스케줄링과 다른 콜백의 영향이 있을 수 있다.

### 12.2 Listener 코드 흐름

1. 노드 이름을 `listener`로 지정한다.
2. `/demo_topic`의 String subscription을 생성한다.
3. 메시지가 수신되면 `callback(self, msg)`를 실행한다.
4. `msg.data`를 `Received:` 형식으로 출력한다.

`self.subscription_`에 subscription을 보관한다. 그 다음 줄의 단독 `self.subscription_` 표현식은 별도의 수신 기능을 추가하지 않는다.

### 12.3 `rclpy.spin()`의 의미

`rclpy.spin(node)`은 실행기가 타이머와 수신 등의 콜백을 처리하도록 한다. 단순히 생성자에서 객체를 만들기만 해서는 주기 발행과 구독 콜백이 계속 실행되지 않는다.

제공 코드는 spin 다음에 `destroy_node()`와 `shutdown()`을 배치한다. `Ctrl+C` 등 예외 상황에서도 정리를 보장하려면 `try/finally` 구조를 추가할 수 있다.

## 13. ROS 2 빌드와 실행 절차

> 아래는 ROS 2 Jazzy가 설치된 Ubuntu의 bash 환경을 기준으로 한 재현 예시이다. macOS 터미널에서 그대로 실행하는 명령이 아니며, 현재 장비에서 실행 검증한 기록도 아니다.

### 13.1 작업공간과 패키지 준비

```bash
source /opt/ros/jazzy/setup.bash
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src
ros2 pkg create --build-type ament_python pubsub_demo --dependencies rclpy std_msgs
```

생성한 `pubsub_demo/pubsub_demo/`에 제공된 `talker.py`와 `listener.py`를 배치한다. `setup.py`에 두 실행 진입점을 등록하고 패키지 이름과 설치 경로가 일치하는지 확인한다.

원본 패키지를 활용한다면 앞 절의 `1_pubsub` 변경 항목을 모두 반영한다. 예시에서는 간단한 String 실습에 필요한 의존성만 생성 명령에 넣었다.

### 13.2 빌드

```bash
cd ~/ros2_ws
source /opt/ros/jazzy/setup.bash
colcon build --symlink-install --packages-select pubsub_demo
source install/setup.bash
```

`source /opt/ros/jazzy/setup.bash`는 기본 ROS 환경을, `source install/setup.bash`는 이 워크스페이스의 설치 결과를 현재 셸에 적용한다. 새 터미널에서는 다시 적용해야 한다.

### 13.3 터미널 A — Talker

```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=23
ros2 run pubsub_demo talker
```

### 13.4 터미널 B — Listener

```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
export ROS_DOMAIN_ID=23
ros2 run pubsub_demo listener
```

### 13.5 로그 형식

```text
[talker] Publishing: "Hello ROS2: 1"
[talker] Publishing: "Hello ROS2: 2"

[listener] Received: "Hello ROS2: 1"
[listener] Received: "Hello ROS2: 2"
```

실제 로그에는 시간과 심각도 등 추가 정보가 포함될 수 있다. Listener를 늦게 시작하면 시작 전에 발행된 모든 메시지를 받는 것은 아니다.

### 13.6 통신 상태 확인

환경을 동일하게 적용한 추가 터미널에서 다음을 실행한다.

```bash
ros2 node list
ros2 node info /talker
ros2 topic list
ros2 topic type /demo_topic
ros2 topic info /demo_topic --verbose
ros2 topic echo /demo_topic
ros2 topic hz /demo_topic
```

`topic hz`는 관찰한 수신 주기를 측정한다. 타이머 설정값 자체를 읽는 것이 아니므로 네트워크·실행 환경의 영향을 함께 반영한다.

## 15. 전체 시스템으로 확장하는 방향

현재 파일은 다음 두 영역의 학습 기반을 제공한다.

| 단계 | 현재 자료에서 확인되는 내용 | 다음 구현 과제 |
| --- | --- | --- |
| 하드웨어 입출력 | 모터 방향, LiDAR 거리, IMU 측정 | 시간 제한, 오류 처리, 보정 |
| ROS 통신 | String 발행·구독 | 센서 메시지와 제어 메시지 정의 |

ESP32 데이터를 ROS 2로 전달하려면 별도의 브리지나 통신 계층이 필요하다. 현재 UART 센서 코드가 자동으로 ROS 토픽이 되는 것은 아니다.

확장 시 검토할 메시지는 다음과 같다.

- IMU: `sensor_msgs/msg/Imu`, 각속도는 ROS 메시지 요구 단위인 rad/s로 변환
- LiDAR: `sensor_msgs/msg/LaserScan`, 거리 mm를 m로 변환하고 각도·시간 필드 구성
- 속도 명령: `geometry_msgs/msg/Twist`, 차체 선속도와 각속도를 바퀴 명령으로 변환

단위 변환만으로 충분하지 않다. 센서 좌표계, timestamp, `frame_id`, 측정 누락 처리도 함께 정의해야 한다. 특히 현재 LiDAR 배열은 오래된 값이 남을 수 있으므로 그대로 하나의 최신 LaserScan으로 내보내기 전에 스캔 구성 방식을 보완해야 한다.

## 16. 문제 해결 가이드

| 증상 | 가능한 원인 | 확인 방법 |
| --- | --- | --- |
| 모터가 움직이지 않음 | 전원, 드라이버 활성화, 배선 | 전원·GND·핀 매핑을 순서대로 확인 |
| 일부 모터 방향이 반대 | 배선·장착 방향 차이 | 개별 시험으로 차체 기준 방향 기록 |
| ESP32 업로드·부팅 실패 | 보드·포트 설정, 연결 회로 | 부팅 관련 핀과 연결 상태 확인 |
| LiDAR 출력 없음 | TX/RX 연결, baud rate | 센서 TX→GPIO 16, 230400 설정 확인 |
| LiDAR 수신 중 멈춤 | 데이터 중단 상태에서 무한 대기 | 패킷 수신 타임아웃 추가 검토 |
| 거리 배열에 이상값 | 오류 패킷·오래된 슬롯 | CRC·confidence·갱신 시각 확인 |
| IMU read failed | 주소·배선·전원 문제 | SDA 21, SCL 22, 주소 0x68 확인 |
| 정지 중 가속도가 0이 아님 | 중력 성분 | 센서 방향과 약 1g 크기 확인 |
| `Package not found` | 환경 미적용·이름 불일치 | 빌드 결과와 `source` 상태 확인 |
| 실행 파일을 찾지 못함 | entry point·설치 위치 오류 | `setup.py`, `setup.cfg` 확인 |
| 토픽은 있지만 수신 안 됨 | Domain ID·QoS·타입 불일치 | `topic info --verbose`와 환경 확인 |
| 테스트 실패 | docstring·스타일 누락 | `colcon test-result --verbose` 확인 |


## 17. 학습 정리

이번 자료에서 가장 중요한 연결은 **전기 신호 → 바이트 → 물리량 → 메시지 → 제어 판단**이다.

모터 실습은 제어 핀과 실제 바퀴 방향의 관계를 확인한다. LiDAR 실습은 연속된 바이트 스트림에서 패킷 경계를 찾고 각도별 거리로 복원한다. IMU 실습은 레지스터에서 읽은 부호 있는 원시 값을 가속도와 각속도로 해석한다. ROS 2 실습은 이러한 데이터를 노드 사이에서 공유할 수 있는 통신 구조를 학습하게 한다.

추가적으로 이해해야 할 점은 다음과 같다.

- UART baud rate와 ROS 메시지 발행 주기는 서로 다른 개념이다.
- 센서 데이터가 수신된다는 사실과 데이터가 최신·유효하다는 사실은 다르다.
- 개별 모터 테스트와 차체 전체 주행 제어는 별도의 단계이다.
- 노드, 프로세스, 터미널, 로봇은 서로 같은 개념이 아니다.
- 토픽 이름·타입 외에도 QoS와 도메인 설정이 통신을 좌우한다.
